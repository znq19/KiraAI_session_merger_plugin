# 会话合并 · kira_session_merger

**版本 2.5.0** · 适用于 KiraAI `core >= 2.6.1`

> 装上它，你的 AI 在哪个群、哪个私聊都是**同一个人**——记得跨会话的经历，分得清"现在在跟谁说话"。

---

## 这是什么？

KiraAI 默认行为：**每个群聊、每个私聊各自独立记忆**，换一个窗口就像换了一个分身，完全不知道刚才在别处说过什么。

这个插件让 AI 拥有**统一人格**。它不另建数据库，而是：

1. 每次回答前，从各会话的官方记忆中各取最近几轮，按时间拼成一条线
2. 告诉 AI 现在在哪个窗口（防止串台）
3. 可选"偷看"未 @ 的消息（像真人刷手机）
4. 把"去私聊/去群里"变成真正的跨窗口路由

**一句话：一个大脑 + 一条时间线 + 组内排队执行。**

---

## 快速开始

1. 把本文件夹放到 `data/plugins/kira_session_merger/`
2. 装依赖：`pip install -r requirements.txt`
3. 重启 KiraAI 或重载插件
4. WebUI → **会话合并** → 打开**启用会话合并**
5. 其他保持默认即可。建议开启**合并组单一 Agent 队列**
6. 发 `/merge s` 看看是否生效

搞定。

## 它能做什么？（小白版）

| 功能 | 大白话解释 |
|------|-----------|
| **读时合并** | 不另存记忆。回答前把相关会话的内容拼一起看 |
| **同一人，不串台** | 知道别处发生过什么，但只在本窗口说话 |
| **组内排队** | 群A在跑时群B来消息先排队，等群A写完再处理群B |
| **跨窗口路由** | "去私聊/去XX群"→ 真切换过去接着干 |
| **硬重开 + 摘要** | 聊太久记忆太长？自动清理旧记录，清理前用 AI 压缩成一段摘要 |
| **软重启** | 只缩短"本次"看的范围，不动磁盘 |
| **偷看** | 偶尔瞄一眼其他会话没 @ 的消息 |
| **命令** | `/reboota` 清空所有会话记忆；`/resum` 压缩当前记忆 |

## 核心玩法

### 读时合并 —— 怎么做到的？

```
回答前：
  群A记忆 ─┐
  群B记忆 ─┤─→ 按时间拼成一条线 ─→ 告诉AI"你现在在群A" ─→ 发给模型
  私聊C记忆 ┘
```

每条 user 消息前面会标注来源（如 `[群A]`），AI 回复不加前缀。

### 组内排队 —— 两个群同时 @ 怎么办？

```
群A在跑 → 群B消息来了 → 排队等待
群A写完落盘 → 等0.4秒 → 开始处理群B（上下文已包含群A刚写的）
```

不会同时开两个 agent，不会乱。

### 跨窗口路由 —— "去私聊继续说"

当你说"去私聊"或调用 `session_send`：
1. 投递通知到目标窗口
2. 目标窗口带着全部上文继续执行
3. 源窗口本轮结束
4. 短时间内重复路由会被拦截

## 推荐合并形态（四种玩法）

安装后在插件配置里调「合并范围」。会话 ID 格式：`qq:gm:群号` / `qq:dm:QQ号`。

### 1. 全部开启合并 —— 不再是分身，就是同一个人

| 配置项 | 建议 |
|--------|------|
| 启用会话合并 | 开 |
| 合并所有群聊 / 所有私聊 | 开 |
| 群聊与私聊互通 | 开 |
| 合并组单一 Agent 队列 | **开**（默认） |

> 最省心的方式。AI 在所有群和私聊里共享记忆，走到哪都是同一个"人"。

### 2. 合并所有群聊 + 私聊 —— 随时了解各个群

| 配置项 | 建议 |
|--------|------|
| 合并所有群聊 / 私聊 | 开 |
| 群聊与私聊互通 | 开 |
| 最大合并会话数 | `6`～`12` |
| 其他会话超时 | 约 `20` 分钟 |

> 群和私聊互相可见，用超时和会话数控制总量，适合群多但不常同时活跃的场景。

### 3. 合并所有私聊 + 特定群

| 配置项 | 建议 |
|--------|------|
| 合并所有群聊 | **关** |
| 合并所有私聊 | **开** |
| 群聊与私聊互通 | **开** |
| 额外会话 | 填重点群 `qq:gm:…` |

> 不想所有群都参与合并？关掉群聊，手动把重要的群加进「额外会话」。

### 4. 只合并特定几个会话

| 配置项 | 建议 |
|--------|------|
| 合并所有群聊 / 私聊 | **关** |
| 额外会话 | **只填**要合并的 sid |
| 排除会话 | 可选 |

> 最精细的控制：只合并你指定的几个会话，其他互不干扰。

> **提示：**「群聊与私聊互通」只决定已参与合并的群和私是否放同一时间线，**不会**单独把全部群/私勾上。合并范围 =「合并所有群/私」+「额外」−「排除」。

## 软重启 vs 硬重开 —— 记忆太长怎么办？**我其实推荐硬重开**

| 模式 | 做了什么 | 风险 | 适用 |
|------|---------|------|------|
| **Soft（软重启）** | 只看最近几轮，磁盘不动 | 低 | 偶尔超限、不想动数据 |
| **Hard（硬重开）** | 删除旧记录，只留最近几轮 + 自动生成摘要 | 中 | 想自动管理、真正释放 token |

**硬重开前的自动摘要**（仅 hard 模式）：
- `off`：不摘要，直接删旧记录
- `sync`（推荐）：先压缩旧历史为摘要写入记忆，再清理（阻塞几秒，精度最高）
- `async`：先清理不阻塞，摘要在后台补写（第一轮看不到摘要）

## Hard 模式 vs CCS（上下文压缩）—— 怎么选？

如果你也装了 [CCS（Context Condensation）](https://github.com/OldTangyuan/KiraAI-ContextCondensation) 插件，可能会纠结：它俩都是管上下文的，用哪个？

### 实际上，本插件的hard模式压缩重开等于是基于[ADS（auto delete session）](https://github.com/znq19/KiraAI_auto_delete_session_plugin) 的合并会话专用版，而ADS本身新版就建立在对CCS的学习和借鉴上。


### 建议：用 Hard 模式，禁用 CCS 。CCS 并不能兼容合并会话后的处理


#### 为什么推荐使用 hard 模式？

1. **够用**：hard 的摘要能覆盖 99% 的场景——被清理的旧对话压缩成一段摘要，AI 通常能自然衔接
2. **省心省 token**：只在超限时和到达持续压缩阈值才触发清理、额外调用LLM，平时零额外开销
3. **一个插件管全部**：合并、路由、排队、清理、摘要——都在一个插件里完成
4. **后台替换无阻塞**：借鉴CCS的思路下，把CCS唯一可能堵塞的一次合并最终摘要生成时机，默认换成了可以先以之前压缩好的拼接摘要先放过来，等后台生成好了，再找一轮放回来。


> 本插件会自动检测 CCS 的存在：默认策略是 `disable_ccs`（自动禁用 CCS）。也可在兼容设置里改为 `ignore` 让两者共存（不推荐，容易冲突）。

## 配置速查

### 合并范围
| 项目 | 默认 | 说明 |
|------|------|------|
| 启用会话合并 | 关 | 总开关 |
| 合并所有群聊 | 开 | 所有群参与合并 |
| 合并所有私聊 | 开 | 所有私聊参与合并 |
| 群聊与私聊互通 | 开 | 群和私聊放同一时间线 |
| 最大合并会话数 | 8 | 一次最多带几个会话的记忆 |
| 额外/排除会话 | 空 | 手动加/减特定会话 |

### 上下文与重启
| 项目 | 默认 | 说明 |
|------|------|------|
| 最大合并轮数 | 10 | 截断上限 |
| 合并token上限 | 30000 | 估算token上限 |
| 超限保留轮数 | 6 | 超限后保留最近N轮 |
| 重启模式 | soft | soft=只看不删 / hard=删旧+摘要 |
| 摘要模式 | sync | hard模式下：off/sync/async |

### Agent 队列
| 项目 | 默认 | 说明 |
|------|------|------|
| 合并组单一Agent队列 | 开 | 组内排队串行 |
| 组锁超时 | 180秒 | 锁超时自动释放 |
| 队列最大长度 | 32 | 排队上限 |

## 常见问题

**Q：token 会不会暴涨？**
A：会比单会话高。用最大合并会话数、超时、轮数/token 上限控制。

**Q：两个群同时 @ 怎么办？**
A：排队串行。先到的先跑，后面的等前一个落盘后再跑。

**Q：路由后源会话没回复？**
A：正常。任务在目标会话继续，源会话可简短确认也可不发言，看 AI 心情。

**Q：怎么确认在生效？**
A：看日志里的 `[MERGER]` 前缀，或用 `/merge s` 命令。

**Q：hard 模式会丢数据吗？**
A：会删除旧记录。但摘要保留了关键信息。担心的话先用 soft 模式。
